# 设计：从参照到虚拟环境的两层流水线

## 目标

骨架为一个桶模拟一个真实站点的模板；环境把一条任务的数据放进骨架，让 agent 只能通过界面操作拿到数据。六条目的，后面的每个机制都要能指回其中一条：

| # | 目的 |
|---|---|
| P1 | 越真实越好 |
| P2 | 知道任务数据能放到哪；放不进去就不放 |
| P3 | agent 拿不到数据的捷径，每条内容都要经过「找 → 行动 → 找」 |
| P4 | 数据必须能拿出来 |
| P5 | 一个骨架装得下同一个桶里的多条任务 |
| P6 | 任务填不满的地方编数据填上；编的数据不能碰撞任务数据，也不能改变任务的答案 |

### P3 的定义

agent 读 DOM、发 HTTP 都可以。禁止的是**一次读取拿到超过一个视图切片的内容**。每条放进界面的内容都必须至少经过一轮：在一个视图里找到它（找），翻页 / 筛选 / 打开 / 导出（行动），在下一个视图里读到（找）。

落到服务端是四条：

1. 每页条数硬上限 = 界面显示的条数；客户端只能要更少，不能要更多
2. 没有按实体的整表端点；只有骨架声明的视图
3. 详情只按键取；键只在列表视图里出现（在链接里），不可枚举的键更好
4. 内容库不在任何可寻址路径上；筛选和排序只对该视图暴露的字段开放（否则隐藏字段成了 oracle）

导出是骨架声明的动作，按真站的范围返回。它是一次「行动」，不是捷径；探针只报告导出的规模，不判失败。

## 从文献借什么

| 借的 | 出处 | 用在哪 |
|---|---|---|
| 从参照写 `description.md`，再照它实现 | VeriEnv `website_description.md` | 第一层步骤 2 |
| 产物 = 代码 + 数据库 + 验证通道，验证通道对 agent 封死 | VeriEnv $(C, D, P)$ | 骨架的形态；部署假设 |
| 建完后 agent 自己驱动自己的站，对照参照找偏差、打补丁 | VeriEnv Playwright 循环 | 第一层构建循环 |
| 生成 → 测试 → 修复循环干了大部分活（27% → 82%） | GUI-Genesis | 两层各一个循环 |
| 种子数据由模型编、要像真的、且当干扰项 | VeriEnv / GUI-Genesis | P6 |
| 只读内容层与可变状态层分开 | PhoneWorld | 内容库 |
| 数据层 / 视图层分离 | InfiniteWeb `website_data.json` | 第二层只换数据 |
| 可取回性没有形式化保证，靠走一遍做构造性证明 | 全体 | `ground_truth.spec.ts` |

我们比他们多一样东西：任务和数据已经存在且自洽。他们要先造任务再造 schema 再造数据；我们只造界面层。

## 骨架是什么

```
skeletons/<bucket>/
  reference/        参照的原始材料：截图、接口响应、DOM 记录、视频帧 —— 什么形态都行
  description.md    从参照写出来的规格：页面、每页显示什么、交互、数据模型、真站没有什么
  skeleton.json     契约：实体、字段、视图暴露表、分区与识别字段、扩展点、第二层可改什么
  app/              前端，照参照复刻；列定义从 skeleton.json 的 views 渲染，不写死
  filler.py         数据生成器：给范例、避让集、排除分区、条数，产出同域的记录
  store/            内容库：store/<entity>.json，每个是一个数组
  verify/           走通 agent 会走的路
```

三个决定：

**服务端驱动，共享引擎。** 表格家族（实体 → 筛选 → 分页 → 详情 → 导出）的骨架共用一个由 `skeleton.json` 驱动的服务端 `envgen/engine/`：filter / sort / page / project / include。骨架只写前端。理由：第二层必须是纯换数据，服务端各写一套第二层就得改代码；agent 看不见服务端，共享不损失真实性。**引擎只覆盖表格家族**；文件树、画布、diff 这类形态的骨架自己写服务端，但同样遵守 P3 的四条。

**前端按 `views` 渲染。** 列定义、详情区块、筛选下拉的字段集都从 `skeleton.json` 读。第二层换字段（`custom_fields`）改的是 `views`，不是代码。

**内容库在静态根之外。** `store/` 只经服务端可达。

### 契约里承担机制的几块

- `views` —— 每个视图的实体、种类（list / detail / export）、暴露字段、页大小、可筛选字段、可排序字段、内嵌的关联。同时是服务端投影的依据（P3 执行）、验证脚本反向断言的依据（P3 检查）、第二层看「字段藏在第几层」的依据（P2）。字段落在哪个槽就决定它在第几层——骨架固定，任务改不了。
- `entities.*.identity` —— 哪些字段相等就算同一条现实记录。碰撞规则的判据。
- `entities.*.partition` —— 任务数据与填充数据靠它隔开的字段（城市、项目、文件夹）。
- `entities.*.fields.*.fill` —— `cosmetic` 的字段可以在任务记录上补值（福利列表、头像）；默认 `never`：状态、判定、数值这类有语义的字段，任务没有就是没有。
- `entities.*.fields.*.names` —— `api` 表示字段名取自真站接口，`builder` 表示是建站者起的名。前者是契约，后者是标签。

## 第一层：参照 → 骨架（每桶一次）

目录 `envgen/build_skeleton/`：

```
抓参照       人 + 浏览器          → reference/        截图是底线，接口 / DOM / CSS 是加分
describe.py  agent 看 reference/  → description.md    页面、交互、数据模型、真站没有什么
build.py     agent 照 description → skeleton.json / app/ / filler.py / store/
                                                      服务端用共享引擎，骨架只写前端
drive.py     agent 驱动自己建的站 → 修 app/           判据是 description.md，对照 reference/ 截图
                                                      找视觉偏差；K=5。走通规格从驱动记录导出
probe.py     机械核对             → 报告              P3 的四条
人看                                                  与参照并排比；像不像只有人能判
```

抓参照是判断，不设规则。`describe` 先写下要建什么再建：建的时候发现规格里没有的东西，是回去补抓或记成偏离的信号，不是顺手加。**`drive` 的判据是 description.md，不是参照**——参照 → 规格是有损的一步，规格漏掉的循环补不回来，所以 `describe` 值得盯。

有意偏离写进 `deliberate_deviations`。真站有就抄，没有就别加；塞不下任务数据就 `disposition: file`。

扩展点（P5）：实体上的 `custom_ok` 与 `must_keep`。参照本身允许扩展的地方才标 `custom_ok`。

验收（P5）：至少拿两条任务做第二层。第二条放不进去，要么是骨架该有一个参照支持的扩展点，要么这条任务不是候选——两种结论都合法，改骨架去迁就不合法。

## 第二层：骨架 + 任务 → 环境（每任务一次）

目录 `envgen/load_task/`：

```
map.py       input/ → mapping.json         哪个文件填哪个实体、哪列填哪个槽、放不下的标 file
validate.py  mapping.json                   覆盖 / 槽位存在 / 结构字段未丢 / 骨架改动有据
load.py      input/ → store/                按映射写入；可推导的结构字段生成，有语义的没有就报错
fill.py      filler.py → store/             围绕任务数据生成干扰记录与装饰字段；写 manifest
verify.py    ground_truth.spec.ts + probe   正向：走路径取回比对；反向：payload 不超视图；探针
repair.py    失败喂回，修 store/ 或规格；K=5，超限丢弃重采
emit.py      改写任务描述；只交付留在磁盘的文件 + URL
```

**`load` 的规则。** 结构字段里可推导的（键、外键、序号）允许生成；有语义的（状态、判定、量值）没有来源就是映射失败，要么骨架为它定义一个明确的「未设置」值，要么这个实体装不下这条数据。不往评分数据里塞编出来的事实。

**`fill` 的规则（P6）。** 填充器收到：任务记录当范例（同域、同值域、同词汇）、任务的识别字段值当避让集、任务占用的分区值当排除集、目标条数。它产出整条记录；装饰字段的补值从产出记录里抄到任务记录的空位上。两条硬规则，`fill` 自己验：

- 识别字段归一化后不得与任何任务记录相等
- 分区值不得落在任务占用的分区里——填充记录在界面上是「别人的数据」，任务按任何谓词取数都取不到它，答案不变

产出 `store/filler.manifest.json`：加了哪些键、给哪些任务记录补了哪些装饰字段。验证脚本据此排除。

**`verify` 的反向面。** 列表视图那次请求的 payload 里不含 `views.<list>.exposes` 之外的字段；探针跑 P3 四条。P4 有 ground_truth，P3 有探针，两边对称。

## 两个循环

| | 判据 | 修的对象 | 终止 |
|---|---|---|---|
| 第一层构建循环 | description.md；参照截图 | app/ | 走通规格过 + 探针过 + 人看过；K=5 |
| 第二层修复循环 | ground_truth.spec.ts；探针 | store/ 与规格本身 | 全绿；K=5，超限丢弃重采 |

修复时不变的东西：不硬写数据值；不把内容挪到更浅的视图；不越过 `layer2_contract`。

---

## 部署假设

环境是一个服务进程，agent 拿到 URL。`store/` 与 `input/` 在 agent 够不着的文件系统里；验证脚本在我们这边跑，直接读文件。被评分的内容只读；可变状态（收藏、勾选）只在 agent 本地且不评分，所以不需要 VeriEnv 那种 SDK，文件系统隔离就够。

仓库里 `envs/<task>/` 把所有东西放一起——那是给我们复现用的。交付给 agent 的只有 `bundle/agent_input/` 和 URL。

## 目的 → 机制

| 目的 | 机制 |
|---|---|
| P1 | reference/；description.md 先行；构建循环对照截图；服务端切片与真站一致 |
| P2 | 实体与槽位；mapping.json；`disposition: file`；`views` 决定字段深度 |
| P3 | 引擎按 `views` 投影、页上限、无整表端点、筛选排序只对暴露字段；store/ 不可寻址；探针 |
| P4 | ground_truth.spec.ts 走 agent 通道做构造性证明；修复循环 |
| P5 | `custom_ok` 扩展点；验收至少两条任务 |
| P6 | filler.py 收范例 + 避让 + 排除分区；manifest；`fill` 自验两条硬规则 |

## 不做的

- 不对参照形态设任何准入条件
- 不做保真度指标，像不像人看
- 不追求可取回性的形式化保证，走一遍就是证明

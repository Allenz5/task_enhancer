# 第二层实例：游戏测试工程师公开岗位样本

任务 `cn-all-remaining-0397-64a67ace`，桶 `job-search-sites`，从 `skeletons/job-search` fork 而来。

## ⚠ 数据是占位的

任务的 3 个输入 zip 不在本地。这里的 24 条样本**结构照任务书原文**
（A01-A12 企业官方岗位页 / B01-B12 公开招聘平台，权重 1.0 / 0.6，15 项能力，5 类岗位原型，4 档责任层级），
但岗位名、公司、城市、经验、学历、描述正文是造的。
zip 到位后**只需替换 `input/samples.json` 并重跑生成脚本**，字段名已经对齐，骨架不用改。
详见 `mapping.json` 的 `data_provenance`。

## 跑

```bash
npx playwright test          # 起静态服务 + 走完 24 条样本的取回链路
python3 -m http.server 5210  # 手动看
```

## 这条任务为什么需要 GUI

任务要求「所有结论必须能回查样本ID、证据短语和来源定位」。
证据短语只出现在**岗位详情正文**里，列表卡上没有 —— spec 里有断言逐条卡这一点。
所以 agent 必须：按城市切换 → 翻页 → 点开 24 条里的每一条 → 读正文。
A 级（企业官方）与 B 级（平台）的来源分层，在界面上就是**公司页 vs 平台搜索列表**两条不同路径。

## 相对骨架改了什么

只改了 `PAGE_SIZE 15 → 5`（`skeleton.json.layer2_contract.allowed` 里允许），
外加换掉 `data/*.json`。**没有给骨架加任何真站不存在的页面或字段。**

## 哪些数据没进 GUI

`02_研究口径与字段字典.docx`、`03_公开资料与来源索引.xlsx`、`05_SHA256清单.txt`、`04_岗位快照目录`
—— 真实招聘站界面里没有对应位置，按 `disposition: file` 留在磁盘。
15 项能力编码、频次、原型判定、JD、面试评分表是 agent 的**产出**，本来就不是输入。

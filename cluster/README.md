# cluster —— 挑出能做成网站的任务，并按界面形态归族

一个环境服务一条任务太贵。要复用，得先知道哪些任务的数据来自同一类界面。

但更前面还有一道闸：**大部分任务的数据根本没有网页界面可复刻** —— OpenSim 的模型
文件、VASP 的算例、酶标仪的原始读数、一个待修复的代码仓库。给它们分类没有意义。

所以这个目录做两件事，顺序不能反：

1. **筛** —— 这条任务的数据来源，我们能不能做出可信的网页复刻（`screen.py` +
   `audit_excluded.py`）
2. **归族** —— 活下来的按**数据形态**分组，一族对应一套界面骨架（`shape.py`）

品类分类（G2 那套）是第三件事，作用是给每个族**找参照产品**，不是分桶依据。

## 为什么不能直接读字段

原始任务里没有任何字段记录数据来源。文件名也无用：出现最多的是
`参考结果.zip`(276)、`输入材料.zip`(259)。

来源这一维度必须构造出来。

## 菜单

`parse_g2.py` 从 `g2.html`（G2「All Categories」页的存档）抽出完整品类表：
**38 个顶层分组 / 223 个父类 / 2238 个品类** → `g2_categories.json` + `g2_tree.json`。

但分类实际用的**不是**这 2238 项，而是 G2 首页导航 `Software` 悬停后那份**精简分类**
—— `g2_slim.json`，**23 个分组 / 289 个品类**。它是给买软件的人做导航用的，留下的
基本都是通用商业软件；垂直行业整支从 491 项砍到 9 项，工程科研那一片 G2 自己就没收。

精简菜单当筛子用：**落得进这 289 项的就是要处理的，落不进的填 null，直接排除。**
拿上一版的结果预估，大约三分之二的任务会落在菜单外 —— 那些正是不需要分类的。

（`menu_keep.json` 和 `menu.py` 里手写的 14 个 `x-` 补充项是上一版的做法，
`blind_test.py` 还在用，`classify.py` 已经不用了。）

## 四步

### `load.py` —— 上游 jsonl → `tasks.json`

每行的 `prompt` 里埋着一段以 `任务证据包：` 开头的 JSON，解析后取 `task.*` 与 `files[]`。
1299 条。`software_and_version` 不抽 —— 它写的是解题工具链，跟数据来源无关，是噪音。

### `find_sources.py` —— 找出原文已经写明来源的任务

这些任务不需要猜，出处就写在题面里。内部跑两轮模型：

**一轮：通读原文列名字。** 模型看到 `task_name` / `industry_domain` / 前 8 个文件名 /
`desc[:900]` / `reqs[:700]` / `verify[:300]`，把可能跟数据出身有关的名字全列出来，
每个附一段 20–60 字的逐字引用。指令明确要求**宁可多给不要漏** —— 连"不得重跑 LAMMPS"
这种拿不准是工具还是来源的也要列，precision 交给二轮。不设数量上限。

**落地校验。** 名字和引用都必须能在原文里字符串匹配上，否则丢弃。这是补回正则的唯一
优点 —— 正则命中一定真实存在，模型抽取不然。另有一份 25 项的通用工具链黑名单
（python / docker / git / …），这些从来不是数据来源。

**二轮：判角色。** 名字出现 ≠ 名字是来源。模型只看到任务名 + 候选名 + 每个候选前后
各 110 字符，判五种角色之一：

| 角色 | 含义 |
|---|---|
| `出处` | 输入数据就是从它导出/下载/快照来的 |
| `产出物` | 这道题要生成的东西，不是输入 |
| `数据里的值` | 名字是数据内容里的一个字段值 |
| `解题工具` | 拿它来算/来跑，或明确说不用跑它 |
| `无关` | 任务自造的项目名，或纯属提及 |

否定句是最典型的陷阱：「不需要运行 VASP 能量计算」里的 VASP 是明确不用的解题工具。

产出 `named_sources.json` —— 来源已知的那些任务，不进分类器。判为非出处的任务什么也
不记录，直接进 `classify.py`；原始响应留在 `runs/` 里可查。

### `classify.py` —— 剩下的按菜单分类

每条问三件事：

- `slug` —— 逐字取自 289 项菜单，**或者填 null**。prompt 里写明"硬凑比 null 更糟：
  null 我们能识别并排除，硬凑的会混进结果里看不出来"。返回菜单外的 slug 会被校验拦下
  并计数。
- `source_real` —— 这份数据在现实里到底有没有真实出处，还是为出题现编的
- `confidence`

prompt 里写了两条纠偏：

**出处优先于场景。** 公开数据集套一个虚构岗位（"你是设备状态监测工程师，工厂有一套
试验台…"），出处仍然是数据集仓库，不许改判成场景里的系统。

**原文里的软件名未必是来源，多数时候不是。** 它可能是解题工具（"使用墨刀完成 PRD"）、
要生成的产出物、数据里的一个字段值、或设计参考 —— 而这些名字往往是整段文字里最显眼
的词，模型很容易顺着它答。这里给的是**规则**不是名单：曾经试过把 `find_sources.py`
判成解题工具的名字逐条标出来注进 prompt，删掉了 —— 那份名单只覆盖抽取命中的那部分
任务，大多数任务根本没有名单，而且它把一次会出错的模型判断写成了分类器推翻不了的
前提。规则对所有任务、所有名字一律生效。

跑法是 A/B 两轮 + **定向第三轮** —— 只有 A、B 不一致或缺失的批次才跑 C，不是全量三倍成本。

### `assign.py` —— 两路合并

`find_sources.py` 钉死的任务只有来源名没有品类，`classify.py` 的只有品类没有产品名。
建站要的是品类，所以这里用 `truth.py` 的对照表把来源名映射成品类，映射不到的单独列出来
—— 那些需要手工往 `truth.py` 里补，否则拿不到品类，而它们恰恰是来源最确凿的一批。

### `blind_test.py` —— 盖住答案再问一遍

验证集是免费的：`find_sources.py` 找出的那些任务来源已知。把名字和所有网址替换成 `※`，
让分类器只凭数据形态、领域词汇、字段与单位判断，再拿 `truth.py` 核对。

只有 `truth.py` 覆盖到的来源能进验证集。这个验证集有系统性偏差 —— 它全部来自原文
写明来源的任务，也就是线索最清楚的那批，**测出的准确率不能外推到没有线索的任务**。

## 跑一遍

纯 stdlib，不需要 venv。`claude -p` 并发超过 5 会静默返回空。

```bash
python3 load.py
python3 find_sources.py     # 130 批抽取 + 约 50 批角色判定
python3 classify.py         # A/B 两轮 + 定向第三轮
python3 assign.py
python3 blind_test.py
```

所有 prompt 与模型响应落在 `runs/<步骤>/<轮次>/`，按批次号缓存，中断了重跑同一条命令
即可续上。想重跑某一轮，删掉那个目录。

### 两道筛的关系

`screen.py` 问"数据是不是来自可浏览的 Web 界面"，那是代理指标；`audit_excluded.py`
问的才是真判据 —— "**这个来源我们能不能做出可信的网页复刻**"。差异是系统性的：
UCI / Zenodo / NCBI GEO / Materials Project / IRIS-FDSN 全都是网站，第一道筛按
"就是几个文件的下载包"把它们排掉了，复核回收了 162 条，其中 42 条构成了一个新的族
（数据集/资料仓库详情页），那是第一次归纳形态族时根本看不到的。

复核用的是**正向词表**：十类确定模拟不了的（每类点具体仪器/软件）+ 九类确定可以模拟的
网站，判不进前者就必须说出来源系统是什么。一致度 720 条 2/2、212 条 3/3，只有 40 条有分歧。

## 三种分桶键的对照

同一批 327 条上量过三种分法（`jury.py` 及其变体，同一套陪审 prompt 与随机对照）：

| | 有细粒度 | 桶数 | 单例 | lift |
|---|---:|---:|---:|---:|
| G2 精简 289 项 | 120 | 46 | 25 | — |
| G2 全量两级+回退 | 207 | 126 | 77 | 0.39 / 0.52 |
| 形态族 | 327 | 12 | 0 | 0.25 |

**结论：桶好不好取决于桶够不够窄，不取决于用哪套词表。** 三种键的 lift 都在
0.25–0.52，而同一套键内部，窄桶（招聘岗位 71%）和宽桶（LIMS 20%、订单 13%）差了四倍。

而且陪审本身只测"两条任务像不像"，那不是操作性问题。真正的判据是"**这条任务的数据
倒不倒得进某个具体骨架**" —— `pipeline/s1_map.py` 已经在做这件事，实测一条
（320 条岗位 + 72 家企业 → job-search 骨架）一轮通过，27 个字段槽填满、新增 0 个，
访谈纪要与内部盘点判 `disposition: file` 留在磁盘。

**所以形态族决定建什么骨架，G2 品类决定照着谁建** —— G2 的品类页直接列着产品，
这正是"一个桶出一个软件"需要的。两者互补，不是二选一。

## 早期方法与教训

在 G2 菜单这条路之前试过一轮**聚类**：TF-IDF → SVD → KMeans，以及 LLM 自己归纳的
站点家族分类法，用 LLM 配对陪审（"这两条任务能不能共用一套界面骨架"）来选方法。
那一轮的代码已删，但踩的坑与具体方法无关，值得留着：

1. **轮廓系数会把你带到 k=617**。它衡量"抱得紧"，跟"能不能共用一个网站"没有关系。
   按它选，最优解等于没聚。
2. **陪审必须带随机对照**。随机抽的任务对，陪审也会给 15–32% 的"能"，
   而且每轮的底噪都不一样 —— 所以跨轮的原始通过率不可比，只能比
   `lift = (p − p₀) / (1 − p₀)`。
3. **配对抽样必须按簇大小加权**。先均匀抽一个簇、再在簇内抽一对，会让 4 个任务的
   小簇和 156 个任务的大簇等权，而大簇装着绝大多数任务。这个 bug 让低 k 的
   通过率从 0.54 虚高到 0.81。
4. **单轮 n=80 不够**。同一个划分三轮测出 92%/76%/81%。要区分相邻的粒度，n 至少 150。
5. **LLM 归纳的分类法读起来最漂亮，实测接近随机**（通过率 41.7%，对照 20%）。
   它按**学科语义**归并来源，而决定界面能否复用的是**数据形态** ——
   "SVG 制图 vs 试井曲线诊断"会被归进同一个家族，但界面骨架完全不同。
   这条是转向 G2 品类菜单的直接原因：品类是按**软件形态**切的，不是按学科。
